# L5.1 — Recovery & Disaster Recovery

> How AXIOM survives failure without duplicate posts, lost work, or security regression. The single-box design keeps DR simple; durability comes from Postgres + R2, not from a sprawl of stateful services.

## 1. Failure modes & responses

<!-- prettier-ignore -->
| Failure | Detection | Automatic response | Operator action |
|---|---|---|---|
| Worker crash during publish or relay delivery | job lock stale | lease expires → the external-side-effect job is dead-lettered with an unknown-outcome incident; no automatic retry | reconcile the provider/channel outcome before any explicitly authorized recovery |
| Box reboot | health check | systemd/Coolify restarts services; PG queue intact (durable) | verify markers |
| Postgres down | connection errors | app fails **closed** (no publish); incidents raised | restore from backup |
| Platform API outage | connector errors | pre-dispatch failures back off; once provider I/O starts, the outcome is dead-lettered as unknown | retry only after provider reconciliation |
| Channel (Relay) unreachable | send failures | pre-dispatch failures back off; once delivery starts, the card job is dead-lettered as unknown | check bot and reconcile before retry |
| ToS engine failure | scan error | verdict defaults to `block` (never `pass`) | inspect model |
| Suspected compromise | anomaly / manual | flip kill-switch (LBI-12) → all egress stops | rotate keys, audit |

## 2. Backups

- **Postgres:** continuous WAL archiving + nightly base backup to R2 (separate bucket/region). PITR enabled.
- **R2 media:** versioned bucket; lifecycle keeps prior versions N days.
- **Secrets:** KEK in KMS (survives box loss); per-org DEKs re-wrappable.
- **Config/markers:** in git; `.axiom/markers` reconstructible from state if needed.

## 3. Restore drill (documented + tested)

1. Provision fresh box; install Coolify (`L4.1` steps 1–2, markers force clean re-run).
2. Restore Postgres via PITR to last consistent point.
3. Re-point R2; verify object integrity via stored `sha256`.
4. Re-wrap DEKs from KEK; app comes up **with egress disabled** (kill-switch default on restore).
5. Run `L5.0` matrix; only when green, flip egress on.

**RPO:** ≤ 5 min (WAL). **RTO:** ≤ 60 min (single-box rebuild). Both measured in a rehearsed drill, not assumed.

### Local logical-recovery evidence (2026-09-11)

`node scripts/rehearse-local-restore.mjs --isolated-fixture` successfully restored
the agent-owned synthetic `axiom_test` database into a fresh temporary database
on the isolated CI container. All 47 public-table row counts/fingerprints and
the compared RLS flags/policy definitions matched. The backup/restore/comparison
phase took 15.5 seconds. The source was unchanged; the temporary database and
dump were removed. No application or worker was started against the restored copy.

A follow-up run took 16.2 seconds and additionally used `SET LOCAL ROLE axiom_app`
on both databases. Two populated tenants retained their own model rows, while
foreign-tenant and unknown-tenant model queries returned zero. The role was
checked to have neither superuser nor BYPASSRLS. This establishes restored
`model_profile` read isolation, not every table's write policies or recovery of
global roles on a new cluster.

A further run took 23.4 seconds and exercised `model_profile` write policies on
the restored copy under both tenant contexts. Own-tenant updates affected the
expected rows; foreign updates/deletes affected zero rows; foreign inserts and
tenant reassignment raised insufficient-privilege errors. All probes rolled
back, and all 47 table fingerprints still matched afterward. Temporary database
cleanup was verified. These checks cover this table, not every write policy.

The script requires explicit opt-in and the isolated-container label, refuses
provider connections or active application clients, and never targets
`axiom-postgres`. It follows the whole-database logical restore flow with
TimescaleDB pre/post-restore hooks; it does not dump global roles.

This is not a PITR, separate-host, R2, secrets, egress-default, or production-size
rehearsal. It does not establish the RPO/RTO targets above or authorize restart
of the real development database. Those requirements remain open.

### Local migration atomicity evidence (2026-09-11)

`node scripts/rehearse-migration-atomicity.mjs --isolated-fixture` exercised an
unchanged copy of the current migration runner against a fresh database in the
labeled disposable container. A synthetic migration contained historical
`BEGIN`/`COMMIT` wrappers. A real PostgreSQL trigger rejected its checksum-ledger
insert: the runner failed and its newly created table was absent, proving DDL
rollback at that boundary. Removing the trigger allowed the migration; a rerun
skipped it; a changed checksum was rejected without applying further changes.
A follow-up also injected an error inside the migration body after its DDL/DML:
the table and ledger entry were absent afterward. The success path's ledger
checksum matched an independently computed SHA-256 of the original file bytes.
Temporary database cleanup was verified, and missing opt-in failed before any
Docker operations. This is a local fault-injection test, not hosted CI, concurrent
migrator testing, arbitrary SQL-parser coverage, or production deployment proof.

## 4. Data-loss guarantees

- Idempotency ledger + content-addressed assets ⇒ replays are safe.
- PG-backed queue ⇒ no in-flight job lost on restart (unlike an in-memory broker).
- Audit hash chain ⇒ any post-incident tampering is detectable.

## 5. Security-preserving recovery

Recovery never weakens invariants: RLS, fail-closed egress, and ToS-block defaults all hold during and after restore. Egress stays off until the full test matrix passes — recovery cannot accidentally resume publishing into an unverified state.
