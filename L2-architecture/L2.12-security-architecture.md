# L2.12 — Security Architecture

Consolidates the cross-cutting security mechanisms referenced by the LBIs. Posture and threat model are in `L0.1`; this is the implementation-level design.

## 1. Envelope encryption (LBI-05)

```
root KEK (age/SOPS or KMS/soft-HSM)
   └ wraps per-org DEK
        └ encrypts social tokens, proxy/WG creds, linkbio provider tokens,
          consent records, any secret column   (XChaCha20-Poly1305 AEAD)
```

- Only ciphertext at rest. DEK unwrapped in a worker's scoped buffer at use time; plaintext zeroized immediately after (`zeroize` in Rust, explicit clear in TS).
- **DEK rotation** re-wraps DEKs under a new KEK without re-encrypting payloads; **secret rotation** is per-credential and revokes old material.
- Secrets never appear in logs (scrubber), API/MCP responses, or Relay messages.

## 2. Tenant isolation (LBI-01)

- Postgres RLS on every tenant table + `SET app.current_org` per connection checkout.
- App-layer guard middleware re-asserts `org_id`/`model_id` scope on every mutation.
- Model-scoped roles carry an additional `model_id ∈ assigned` predicate.
- Pooled connections reset `app.current_org` on release to prevent bleed.

## 3. Signed control & webhooks (LBI-04)

- **Relay commands:** `HMAC-SHA-256(channel_key, {bundle_id, action, nonce, exp})`; single-use nonce store; TTL check; channel-identity binding; audited signer + token id. Sensitive actions excluded from Relay.
- **Inbound webhooks** (platform callbacks, external dev): HMAC signature verification + timestamp/nonce replay protection; reject on skew.
- **MCP/REST tokens:** short-lived signed JWT (`kid` rotation); asymmetric EdDSA where third parties verify; capability + tier + model claims.

## 4. Hash-chained audit (LBI-06)

- `audit_log(seq, org_id, actor, action, target, meta, prev_hash, hash)` where `hash = H(prev_hash ‖ canonical(entry))`.
- Append-only (no UPDATE/DELETE grants; enforced by DB role + trigger).
- A periodic verifier walks the chain; any break raises a Sev-1 tamper alarm and pages the Relay.
- Every state-changing action (approve, publish, override, network-config change, kill switch, agent grant) writes an entry.

## 5. Fail-closed egress (LBI-02)

OS-enforced via per-model netns with no host default route; health-gated; never falls back to host IP. Detailed in `L2.6`.

## 6. Idempotency (LBI-03)

`idempotency_ledger` unique on `H(model_id, asset_hash, platform, slot)`; publish jobs commit their ledger entry in the same transaction as the state change; replay returns the stored result. Guarantees no double-post under retries or DLQ replay.

## 7. Least privilege & confinement

- Agents see only tier-permitted tools (manifest confinement, `L2.11`).
- Rust hot-path holds `NET_ADMIN` only where required (netns/WG) and nothing else; other services drop capabilities.
- Service accounts are per-plane with minimal DB grants (e.g., the audit role can INSERT but not UPDATE/DELETE audit rows).

## 8. Supply chain & build

- `cargo audit`, `osv-scanner`/`npm audit`, SAST, and secret-scanning pre-merge.
- Pinned dependencies; reproducible container builds; SBOM per release.
- Marker-gated deploy scripts (`sh -n` verified) with append-only provisioning ledgers (LBI-10).

## 9. Backups & DR

- Postgres PITR (WAL shipping) → RPO ≤ 15 min; encrypted off-box backups (pgBackRest).
- R2 versioning for media; periodic restore drills (`L5`).
- Documented, idempotent recovery per subsystem (`L5.1`).

## 10. Data lifecycle & privacy

- Fan CRM data minimized, encrypted, deletable on request; configurable retention.
- Consent & Records Vault gates publishing (LBI-12) and is itself envelope-encrypted with strict access logging.
