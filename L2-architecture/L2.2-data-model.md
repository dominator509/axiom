# L2.2 — Data Model

Multi-tenant, RLS-enforced (LBI-01), Postgres 16 + TimescaleDB + pgvector + Postgres queue. This is the logical model; concrete DDL is in `L3-specification/L3.1-database-ddl.md`.

## Entity tree

```
organizations
 ├ users                         (RBAC: Owner, Chatter, Content Creator, Model)
 ├ api_keys                      (per-org, envelope-encrypted platform tokens)
 ├ audit_log                     (hash-chained, append-only — LBI-06)
 ├ org_settings                  (publishing_enabled flag, budgets, retention)
 └ models                        (talent profiles)
     ├ social_accounts           (per-platform, encrypted creds, capability cache)
     ├ model_network_configs     (egress: direct/socks5/http/wireguard/vpn + health)
     ├ content_assets            (media library; variants; watermark meta; crop tracking)
     ├ asset_variants            (per-crop/per-caption variants; performance link)
     ├ scheduled_posts           (queue-linked; platform set; status; attempts; idempotency_key)
     ├ post_targets              (per-post × per-platform: caption, hashtags, price, tos_score, status)
     ├ pre_post_runs             (abstracted script execution records)
     ├ analytics_snapshots       (TimescaleDB hypertable: followers/engagement over time)
     ├ post_performance          (TimescaleDB: per-post metrics over windows)
     ├ viral_recipes             (labeled high-performers + full generative recipe)
     ├ viral_embeddings          (pgvector: caption/hook embeddings → recipe_id)
     ├ bandit_state              (arm weights per (model,platform,context))
     ├ seo_aeo_rankings          (keyword + AI answer-engine positions)
     ├ fanvue_metrics            (subs, earnings, messages, tips via MCP)
     ├ fan_crm_contacts          (high-value fan; tags; interaction history)
     ├ fan_touchpoints           (unified timeline across all connectors + Fanvue)
     ├ custom_requests           (ticketing: Pending/Filming/Editing/Delivered)
     ├ campaigns                 (grouped pushes + KPIs)
     ├ trigger_rules             (IFTTT: condition → action, per-platform thresholds)
     ├ linkbio_providers         (0..n active: native/fanlynks/linktree/beacons + config)
     ├ linkbio_analytics         (normalized clicks/visits/sources across providers)
     ├ short_links               (built-in shortener; UTMs; attribution ties)
     ├ consent_records           (Consent & Records Vault; expiry — LBI-12)
```

## RLS model (LBI-01)

Every tenant table has `org_id`. A `SET app.current_org = '<uuid>'` is issued on each pooled connection checkout from the authenticated principal. Policies:

```sql
-- pattern applied to every tenant table
ALTER TABLE <t> ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON <t>
  USING (org_id = current_setting('app.current_org')::uuid)
  WITH CHECK (org_id = current_setting('app.current_org')::uuid);
```

App-layer guards re-assert `org_id` on every mutation (defense in depth). Model-scoped roles (Model, Chatter, Content Creator) add a second predicate on `model_id ∈ assigned set`.

## TimescaleDB hypertables

- `analytics_snapshots(model_id, platform, ts, followers, engagement, reach, …)` — chunk by day.
- `post_performance(post_id, platform, ts, views, likes, saves, shares, ctr, conversions, retention, …)` — chunk by hour; continuous aggregates roll up to 1h/1d for dashboards and the viral loop.

## pgvector (viral loop)

- `viral_embeddings(recipe_id, model_id, platform, embedding vector(1024), created_at)` with an HNSW index for top-K similarity. Populated when a post is labeled a high-performer (see `L2.8`). Retrieval is `ORDER BY embedding <=> :query_vec LIMIT k` filtered by `model_id`/`platform`.

## Postgres-backed queue

- `river_job` / `pgmq` tables hold durable jobs: `publish`, `generate`, `ingest_metrics`, `tos_score`, `watermark`, `clip`, `scrape`, `relay_dispatch`, `dead_letter`. Jobs commit in the same transaction as their domain writes (e.g., a `publish` row + its idempotency ledger entry), which is how LBI-03 is guaranteed atomically.
- `idempotency_ledger(key, result_hash, created_at)` — unique on `key = H(model_id, asset_hash, platform, slot)`.

## Key relationships & invariants in schema

- `scheduled_posts` 1—n `post_targets`: one logical post fans out to N platform targets, each with its own caption/hashtags/price/tos_score/status. This is what makes "Approve for X + Reddit only" a first-class operation (J1).
- `content_assets` 1—n `asset_variants`; `asset_variants` link to `post_performance` so the best crop is measurable (F-13).
- `viral_recipes` snapshots the exact `{S3 config, caption, hashtags, time, format, hook, thumbnail_features, tos_score}` used, so it can be replayed/injected.
- `consent_records.expires_at` gates `models.publishing_allowed` (LBI-12).
