# L2.4 — Link-in-Bio Providers (Pluggable, All Optional)

## Requirement satisfied

The system must **not require** Fanlynks or Linktree (or both). Providers are optional and composable: a model may run **zero, one, or several simultaneously**. The default requires nothing external.

## Current status and release target

The source currently recognizes all four provider identifiers and includes partial provider-specific routes, profile records, redirect/analytics code. Native is the built-in hosted page. Those records and code paths do not establish a complete external connection: verified provider authorization, link synchronization, remote readback, permission validation, revocation, and teardown remain unaccepted. A `linkbio_provider` database row alone is not evidence that an external provider is connected.

The production-readiness target includes all four providers as optional, composable choices. Native must work with no external provider. Each external provider becomes selectable only after its supported provider contract and full lifecycle have been verified with a dedicated account; provider availability or missing metrics must be reported honestly.

## Provider abstraction

The API and database contract recognize four provider identifiers, selected per model via `linkbio_providers` rows (0..n active). This data contract is not evidence of four complete adapters. Native is the built-in provider; the external rows below describe the approved release target and current implementation limits:

| Provider | Requires | Deploy | Analytics source |
|---|---|---|---|
| **Native** (default) | nothing external | rendered by the CRM at the edge (Cloudflare-cached route `m.<domain>/<slug>`) | first-party (our own click events → `linkbio_analytics`) |
| **Fanlynks** (optional) | the user's Fanlynks repo | provisioned Docker container / Vercel subdomain **only if enabled** | GA4/GTM/Meta Pixel ingest |
| **Linktree** (optional) | Linktree account | none (their hosting) | Linktree API |
| **Beacons** (optional) | Beacons account | none | Beacons API |

### Native provider (new, F-52)
A CRM-hosted link page: server-rendered, Cloudflare-cached, themeable per model (links, colors, branding, avatar), backed by the built-in shortener (F-22). Operators can also select an actually published model post, validate its Fanvue destination, and create an audited short link with platform and post-target UTMs (F-23). Its public redirect records the owned link click before adding the saved UTMs and forwarding. Because it is part of the app, it is the **cheapest, fastest, and zero-dependency** default — a new model is instantly live with a link page and first-party analytics, no external service touched.

### Fanlynks provider (F-49, release-target adapter)
The source includes a Fanlynks-named hosted page and read-only analytics paths, but full external provisioning, synchronization, verified remote readback, and teardown have not been accepted. The release target may provision a Fanlynks instance and synchronize model links/branding only through a verified supported contract; analytics must reflect metrics actually returned by the connected source.

### Linktree / Beacons providers (F-50, F-51, release-target adapters)
The source includes provider-specific profile/analytics handling and tracked-link paths. It does not yet establish supported account authorization, remote link synchronization/readback, permission validation, or revocation. Do not describe either provider as verified or connected until its complete lifecycle passes dedicated-account acceptance.

## Composition & normalization

- A model's production `linkbio_providers` set may contain any independently enabled subset of `{native, fanlynks, linktree, beacons}` after each external contract and lifecycle is verified.
- **Which link do we hand out?** A per-model **primary provider** setting decides the canonical URL injected into social bios, funnel DMs, and content-link shares. Non-primary providers still collect analytics (useful for A/B'ing link pages).
- **Normalized analytics (F-53):** Native feeds first-party click analytics today. Each accepted adapter feeds the common `linkbio_analytics` shape `(provider, ts, visits, unique, source, clicks, ctr, conversions)` where the provider supplies that metric; unsupported metrics remain explicitly unavailable and are never reported as zero.
- **Attribution tie (F-23):** Native per-post short links carry a published post-target ID and platform in their UTMs. The Attribution Engine joins those first-party short links and click events to ingested Fanvue subscription/PPV events; ROI is reported only when recorded campaign costs support a currency-aligned calculation. External adapters remain outside this flow until implemented.

## Deployment engine changes vs v1

- v1 auto-deployed Fanlynks per model. **No external instance deploys by default** — Native needs no deploy. Fanlynks provisioning occurs only when explicitly enabled and accepted.
- Before external activation, disabling a provider must deprovision its instance (Fanlynks) or revoke its tokens (Linktree/Beacons), stop ingesting, and retain historical analytics.

## Data model touchpoints

`linkbio_providers(model_id, kind, is_primary, config_encrypted, status, provisioned_at)` and `linkbio_analytics(model_id, provider, ts, …)` (see `L2.2`, DDL in `L3.1`). Provider configs (API tokens) are envelope-encrypted like any other secret (LBI-05).
