# L2.4 — Link-in-Bio Providers (Pluggable, All Optional)

## Requirement satisfied

The system must **not require** Fanlynks or Linktree (or both). Providers are optional and composable: a model may run **zero, one, or several simultaneously**. The default requires nothing external.

## Provider abstraction

A `LinkInBioProvider` interface with four implementations, selected per model via `linkbio_providers` rows (0..n active):

| Provider | Requires | Deploy | Analytics source |
|---|---|---|---|
| **Native** (default) | nothing external | rendered by the CRM at the edge (Cloudflare-cached route `m.<domain>/<slug>`) | first-party (our own click events → `linkbio_analytics`) |
| **Fanlynks** (optional) | the user's Fanlynks repo | provisioned Docker container / Vercel subdomain **only if enabled** | GA4/GTM/Meta Pixel ingest |
| **Linktree** (optional) | Linktree account | none (their hosting) | Linktree API |
| **Beacons** (optional) | Beacons account | none | Beacons API |

### Native provider (new, F-52)
A CRM-hosted link page: server-rendered, Cloudflare-cached, themeable per model (links, colors, branding, avatar), backed by the built-in shortener (F-22) so every outbound link is a tracked `short_link` with per-post UTMs (F-23). Because it is part of the app, it is the **cheapest, fastest, and zero-dependency** default — a new model is instantly live with a link page and full first-party analytics, no external service touched.

### Fanlynks provider (F-49, now optional)
When (and only when) enabled, the Deployment Engine provisions a Fanlynks instance (Docker/Vercel subdomain), injects the model's links/colors/branding via env/config API, and ingests GA4/GTM/Meta Pixel data via the Google Analytics Data API and Meta Graph API into TimescaleDB. Never auto-provisioned on model creation anymore.

### Linktree / Beacons providers (F-50, F-51, optional)
OAuth/API integrations that push the model's link set and pull click analytics. Enabled independently.

## Composition & normalization

- A model's `linkbio_providers` set can be `{}`, `{native}`, `{native, linktree}`, `{fanlynks, beacons}`, etc.
- **Which link do we hand out?** A per-model **primary provider** setting decides the canonical URL injected into social bios, funnel DMs, and content-link shares. Non-primary providers still collect analytics (useful for A/B'ing link pages).
- **Normalized analytics (F-53):** all providers feed a common `linkbio_analytics` shape `(provider, ts, visits, unique, source, clicks, ctr, conversions)`. The dashboard shows a unified panel ("Link traffic today: 1,500 · Top source: X · CVR 5%") regardless of which providers are active, and can break down by provider.
- **Attribution tie (F-23):** clicks from any provider that pass through the built-in shortener carry UTMs; the Attribution Engine joins click events to Fanvue subscription/PPV events (via MCP) to prove per-post ROI.

## Deployment engine changes vs v1

- v1 auto-deployed Fanlynks per model. **v2 deploys nothing by default** — the Native provider needs no deploy. The engine only acts when a model enables an external provider, and it tracks provisioning state in an append-only ledger with marker semantics (LBI-10) so re-runs SKIP rather than double-provision.
- Teardown is first-class: disabling a provider deprovisions its instance (Fanlynks) or revokes its tokens (Linktree/Beacons) and stops ingesting, while retaining historical analytics.

## Data model touchpoints

`linkbio_providers(model_id, kind, is_primary, config_encrypted, status, provisioned_at)` and `linkbio_analytics(model_id, provider, ts, …)` (see `L2.2`, DDL in `L3.1`). Provider configs (API tokens) are envelope-encrypted like any other secret (LBI-05).
