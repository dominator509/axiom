# L0.1 — Security Posture, Compliance & Risk Register

## 1. Threat model (abridged STRIDE)

| Threat | Vector | Mitigation | LBI |
|---|---|---|---|
| **Spoofing** | Forged Relay "approve/publish" command from a leaked chat | HMAC-signed, nonce'd, TTL'd, single-use command tokens; channel identity binding | LBI-04 |
| **Tampering** | Altered audit trail to hide an action | Hash-chained append-only audit; periodic chain verification | LBI-06 |
| **Repudiation** | "I never approved that post" | Every approval records signer, channel, token id, timestamp | LBI-04, LBI-06 |
| **Information disclosure** | Token/proxy-cred exfiltration; cross-tenant read | Envelope encryption + zeroization; RLS + app guards; secrets never logged | LBI-05, LBI-01 |
| **Denial of service** | API abuse of CRM MCP/REST | Per-token rate limits; global kill switch; queue backpressure | LBI-11 |
| **Elevation of privilege** | Agent exceeding its permission tier | Capability-scoped short-lived MCP tokens; per-model matrix; publish gate | LBI-04, LBI-07 |
| **Cross-account association** | Egress leak linking two models | Fail-closed egress in netns; health-gated binding | LBI-02 |
| **Double-post / retry storm** | Queue retry after partial success | Idempotency keys; dedupe ledger | LBI-03 |

## 2. Cryptography

- **At rest (secrets):** XChaCha20-Poly1305 AEAD. Per-org **Data Encryption Key (DEK)** wrapped by a root **Key Encryption Key (KEK)**. Self-hosted: KEK held via `age`/SOPS or an on-box HSM/soft-HSM; managed: cloud KMS. DEK rotation re-wraps without re-encrypting all data; secret rotation is per-credential.
- **At rest (bulk data):** full-disk / volume encryption + Postgres TDE-equivalent via encrypted volumes; R2 SSE for media.
- **In transit:** TLS 1.3 everywhere; internal service mesh mTLS optional on multi-box topology.
- **Signing:** Relay commands and webhook callbacks use HMAC-SHA-256 with per-channel keys; MCP/REST use short-lived signed bearer tokens (JWT with `kid` rotation) — asymmetric (EdDSA) where third parties verify.
- **Zeroization:** decrypted secrets live in a scoped buffer in the Rust/TS worker, wiped (`zeroize`) immediately after the outbound call.

## 3. Secret & credential lifecycle

1. Operator enters a platform token / proxy cred in the dashboard (TLS).
2. BFF encrypts with the org DEK before it touches disk; only ciphertext is persisted.
3. At job time, the worker fetches ciphertext, unwraps DEK via KEK, decrypts in memory, uses it, zeroizes.
4. Rotation and revocation are first-class dashboard actions; revocation invalidates cached material immediately.
5. No secret is ever returned by an API/MCP tool, logged, or included in a Relay message (LBI-05).

## 4. Compliance & records (adult-content operations)

This is a legitimate creator-management concern and is treated as load-bearing.

- **Consent & Records Vault:** encrypted store of model releases, government-ID age verification artifacts, and per-shoot consent documentation, with expiry tracking. Publishing is blocked for any model lacking valid, in-date records (LBI-12).
- **Platform ToS stance:** the ToS Risk Engine classifies content and blocks/upgrades-to-override any publish that exceeds a platform's threshold (LBI-07). The system's posture is **compliance-forward**: it exists to keep accounts within each platform's stated rules, not to defeat platform safety systems. Network isolation is justified by account-integrity, privacy, and security — standard multi-account agency hygiene — not deception of fraud/abuse detection.
- **Data subject handling:** fan CRM data is minimized, encrypted, and deletable on request; retention windows are configurable per org.
- **Auditability:** the hash-chained audit supports after-the-fact review of who approved what, when, and through which channel.

## 5. Risk register

| ID | Risk | Likelihood | Impact | Response |
|---|---|---|---|---|
| R-01 | A platform changes/removes its posting API (esp. Snapchat, TikTok) | High | Med | Capability matrix + graceful degrade to link-share/manual-assist; connector versioning; feature-flag per capability. |
| R-02 | Platform ToS enforcement action on a managed account | Med | High | ToS gate; per-model isolation; conservative default thresholds; override audit. |
| R-03 | Fanvue MCP surface changes | Med | High | Adapter isolation; contract tests against `mcp.fanvue.com`; pinned tool versions. |
| R-04 | Egress provider outage | Med | Med | Fail-closed (no leak); multi-provider config per model; health-gated failover to an alternate approved egress, never to host. |
| R-05 | Secret compromise | Low | High | Envelope encryption; rotation; least-privilege tokens; no plaintext at rest. |
| R-06 | LLM cost blowout | Med | Med | TOKENKILLER >97% cache; local vLLM fallback; per-org budget caps + alerts. |
| R-07 | Relay channel account takeover | Low | High | Signed single-use commands; channel identity binding; sensitive actions (network config, autonomous grant) require dashboard, not Relay. |
| R-08 | Viral-loop overfitting to a stale pattern | Med | Low | Bandit exploration floor; recency-decayed weighting; per-platform drift detection. |
| R-09 | Double-post during incident recovery | Low | Med | Idempotency keys; dead-letter replay is idempotent by construction. |
| R-10 | Partial deploy leaves inconsistent state | Med | Med | Greenfield marker guard (SKIP/FAIL); append-only ledgers; documented recovery. |

## 6. Security review cadence

- Pre-merge: secret-scan, dependency audit (`cargo audit`, `npm audit`/`osv-scanner`), SAST.
- Per-release: LBI verification suite (`L5-verification/`), audit-chain verification, egress fail-closed drill.
- Quarterly: key rotation, penetration review of Relay + MCP surfaces, restore-from-backup drill.
