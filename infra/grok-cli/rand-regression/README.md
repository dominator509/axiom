# RNG logging-boundary regression

Test-only coverage for RUSTSEC-2026-0097. Both rand release series explicitly
enable the deprecated `log` feature. The patched versions make that feature a
no-op, removing the synchronous callback through which a custom logger could
re-enter the same thread-local RNG while it is mutably borrowed.

```sh
cargo test --locked --manifest-path infra/grok-cli/rand-regression/Cargo.toml
```

The test first checks that its logger is active, then exercises both RNGs on
four threads with scalar reads, byte fills and cloned handles beyond the 64 KiB
reseeding threshold. It requires zero RNG callbacks. Generated bytes are never
logged. This is a callback-boundary regression, not an entropy quality test.

The separate baseline deliberately pins affected versions and must fail:

```sh
cargo test --locked --manifest-path infra/grok-cli/rand-regression/baseline/Cargo.toml
```

Windows execution passed for the patched versions and failed for the baseline
with `[72, 72]` observed callbacks versus `[0, 0]` expected. The logger observes
callbacks but does not re-enter an RNG, so the baseline does not deliberately
execute the aliasing undefined behavior. No Miri claim is made.

With the additional failure test running concurrently, the later baseline run
reported `[102, 72]` and also failed the silent-continuation assertion. Exact
nonzero baseline callback counts are not contractual; concurrent failure-path
logging can add events. Patched versions must still produce zero callbacks.

These standalone manifests are not linked into the CLI. Their transitive
dependency resolution is separate from the candidate CLI lockfile; consumer
compatibility must also be verified against that lockfile. Current candidate
source/lockfile inspection indicates its rand logging features are disabled;
this update is preventive hardening, not a confirmed exploitable Grok path.
The shipped lock patch is checked against hash-pinned upstream source and these
two harness version/checksum pairs by `scripts/check-grok-rand-contract.mjs`.
Its negative controls reject a reverted RNG patch and harness checksum drift.
This binds the tested direct dependencies, not all transitive harness packages,
to the shipped candidate.

## Entropy failure compatibility

The patched releases panic when periodic reseeding fails rather than silently
continuing with the previous RNG state. A deterministic failing entropy source
tests the public rand 0.8 reseeding wrapper. Linux additionally tests both real
thread-local RNGs in disposable child processes, after successful initialization:

```sh
sh infra/grok-cli/rand-regression/test-linux.sh --offline
```

The runner first tests the default backend, then enables the explicit
`entropy-fault-injection` feature with a **test-only** `linux_raw` entropy backend.
The child denies its own getrandom syscall with EIO and forces periodic
reseeding; the parent requires exit 101 and the expected reseeding panic, with
no post-loop success marker. The ignored child entry point is explicitly run
by the parent test, not skipped coverage. Neither random bytes nor credentials
are printed. This does not prove that no buffered random bytes can be produced
between entropy denial and the next reseed.

Blocking the syscall alone did not reliably fault rand 0.10's default libc
backend in the local container. Consequently the syscall-backend result must
not be described as default-backend failure injection or applied to production
compiler flags. Both passes are required in CI. Local Linux results: default
2 passed; fault-injection 3 passed, 1 child entry point ignored by the outer
runner and invoked explicitly by its parent. Rust formatting also passed.

Independent patch review prompted both the entropy-failure coverage and the
shipped-lock binding. Full CLI rebuild and installed-runtime acceptance for
this candidate remain outstanding; standalone tests are not release proof.
