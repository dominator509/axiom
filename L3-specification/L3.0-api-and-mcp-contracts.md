# L3.0 — API & MCP Contracts

Representative contracts; the full OpenAPI doc is generated from the Hono route schemas at build time. All routes enforce RBAC + RLS + rate limits + audit. Auth: Bearer (REST) or MCP capability token.

## Conventions

- Base: `https://crm.<domain>/api/v1`
- All list endpoints paginate (`cursor`, `limit`).
- Mutations require an `Idempotency-Key` header where they touch the outside world.
- Errors: RFC-7807 problem+json with `correlation_id`.

### F-90 FanThynks platform affiliate API surface (source-wired; runtime gates remain open)

F-90 is a FanThynks platform-acquisition program for partners who refer
creators to the SaaS. It is not an organization-scoped affiliate builder,
creator referral program, or tenant resale control plane. Platform routes reuse
the existing platform/operator authorization, audit and idempotency machinery;
the public referral handoff and authenticated claim use the existing session
boundary:

```text
GET    /platform/affiliate/program
GET    /affiliate/r/{referralToken}                    public click attribution + same-origin login redirect
POST   /affiliate/claim                                authenticated, idempotent referral identity stitch
POST   /platform/affiliate/partners
PATCH  /platform/affiliate/partners/{partnerId}
GET    /platform/affiliate/partners/{partnerId}/export  partner-owned data projection; deletion is audited revoke, not attribution erasure
POST   /platform/affiliate/campaigns
GET    /platform/affiliate/campaigns/{campaignId}/report
POST   /platform/affiliate/conversions/reconcile
GET    /platform/affiliate/payouts/export              emits a CSV/JSON artifact and records an audit-safe export receipt
POST   /platform/affiliate/holds/{holdId}/resolve
```

The durable source contract covers partner/campaign links, immutable click and
identity-stitch events (the authenticated claim attaches only the signed-in
creator identity), a clearly identified SaaS conversion event, derived
commission/reversal views, fraud holds, payout export, disclosures and audit.
Attribution is recomputable and idempotent. No route directly charges a
customer, pays a partner, publishes content or changes provider state; those
effects require their own existing approval and idempotency fences. Cross-tenant
creator and customer data is never exposed to a partner. A selected external
stack must permit the required modification and redistribution/resale model;
license fit is not a security or production-hardening certification.

The public referral redirect accepts no destination URL. It records a bounded,
anonymous `click` event only when the program, partner and campaign are active,
then redirects to the same-origin `/login?affiliate_ref=...` flow. The opaque
token is an onboarding handoff; conversion reconciliation remains a separate
owner/billing integration boundary and must name a creator with an earlier
`identity_stitch` for the same campaign. Active program, partner disclosure and
campaign checks are repeated at reconciliation time; a missing or mismatched
stitch is rejected rather than converted into unattributed commission. A
`subscription_refunded` reconciliation must also name the source billing event
key for a prior started or renewed conversion owned by that same creator and
campaign; a refund without that binding is rejected.

### F-91 Patreon API surface (planned, not source-wired by this document change)

Patreon reuses the existing model-scoped social-account connect/revoke
contract, but its user-facing integration surface is read/sync oriented:
campaign identity, membership/tier state, cursor-paginated post history,
webhook health and last-sync/reconciliation status. The implementation may
add model-scoped read/sync routes under the existing API namespace, but must
not add a generic Patreon `publish_now` action while the official v2 contract
only documents post-read access and inbound post lifecycle webhooks. Manual
assist uses the existing Relay card and approval/audit path. No member
mutation, DM, payout, email/address scope or provider metric is implied.

Native Link-in-Bio `config.links`, when supplied, must be an array. Each entry requires a nonempty trimmed label (at most 120 characters) and HTTP(S) URL (at most 2048 characters). Optional `utm` values must be nonempty strings of at most 120 characters, with keys matching `^utm_[a-z][a-z0-9_]{0,31}$`. Invalid entries reject the entire mutation with 400 before stored content is replaced; an empty array explicitly clears links. Unrelated configuration fields are preserved in the supplied configuration object.

## MCP tool surface (dynamic per tier — see `L2.11`)

Tools mirror the REST verbs but are gated by tier and marked `requires_approval`. Illustrative set:

| Tool | Tier ≥ | requires_approval |
|---|---|---|
| `crm_read_analytics` | Viewer | no |
| `crm_read_inbox` | Viewer | no |
| `crm_generate_photoshoot` | Operator | yes |
| `crm_reply_dm` | Operator | no (SFW-gated) |
| `crm_deploy_linkbio` | Operator | no |
| `crm_create_content` | Manager | yes |
| `crm_schedule_targets` | Manager | yes |
| `crm_publish_now` | Autonomous | n/a (allowed) |
| `crm_set_network` | Autonomous | dashboard-grant only |

`requires_approval: true` tools return a `bundle_id` that surfaces on the Relay; they never publish directly (LBI-04).

## Webhooks (outbound)

Signed (HMAC + timestamp + nonce). Events: `post.published`, `post.failed`, `bundle.generated`, `sub.expired`, `viral.labeled`, `incident.sev1`, `tos.blocked`. Consumers verify signature and dedupe on `event_id`.

## Rate limiting

Per-token buckets; `429` with `Retry-After`. Publishing to platforms is additionally governed by per-platform buckets in the worker (`L2.3`).

## Caption revision lifecycle

`POST /bundles/{bundleId}/revise` requires nonblank instructions (maximum 2000 characters). It atomically sets the bundle to `revising`, invalidates the prior ToS verdict, and enqueues the existing `content.generate` worker. The response describes queued work, not completed generation. The worker revises each existing platform caption using the operator instructions in S3, preserves the asset and hashtags, then returns the bundle to `generated` and enqueues a new `tos.scan`. This does not regenerate image/video assets.

Provider failure or unchanged output fails the job without changing captions or restoring approval. Failed generation is retried/replayed through the existing job/incident controls. Approval stays blocked while revision or its ToS scan is pending or failed.

The report carries a `revisionId` through scanning and into each Relay card. REST approve, revise, and reject actions on a revised bundle must echo this value; stale browser requests and stale Relay cards are rejected. These REST checks hold the bundle row lock through the mutation. Relay `revise`/`regenerate` use the same caption-generation path, accepting optional instructions or explicit default caption-revision instructions. Relay calls do not impersonate an AXIOM subscription user; they require an available provider that can operate without a user subscription identity.

Relay `edit_caption` follows the same approval invalidation rule without invoking generation: it stores the supplied text, assigns a fresh revision identifier, and enqueues a new ToS scan. Previously approved pending targets are canceled under their row locks, so even already-claimed jobs cannot publish the changed text using old approval. Any provider ID, published outcome, or unresolved dispatch blocks the edit until reconciliation. The operator must review and approve again, including selecting the new schedule.
