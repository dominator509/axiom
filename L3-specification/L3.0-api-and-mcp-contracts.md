# L3.0 — API & MCP Contracts

Representative contracts; the full OpenAPI doc is generated from the Hono route schemas at build time. All routes enforce RBAC + RLS + rate limits + audit. Auth: Bearer (REST) or MCP capability token.

## Conventions

- Base: `https://crm.<domain>/api/v1`
- All list endpoints paginate (`cursor`, `limit`).
- Mutations require an `Idempotency-Key` header where they touch the outside world.
- Errors: RFC-7807 problem+json with `correlation_id`.

## MCP tool surface (dynamic per tier — see `L2.11`)

Tools mirror the REST verbs but are gated by tier and marked `requires_approval`. Illustrative set:

| Tool | Tier ≥ | requires_approval |
|---|---|---|
| `crm_read_analytics` | Viewer | no |
| `crm_read_inbox` | Viewer | no |
| `crm_generate_photoshoot` | Operator | yes |
| `crm_reply_dm` | Operator | no (SFW-gated) |
| `crm_deploy_linkbio` | Operator | no |
| `crm_create_content` | Manager | yes |
| `crm_schedule_targets` | Manager | yes |
| `crm_publish_now` | Autonomous | n/a (allowed) |
| `crm_set_network` | Autonomous | dashboard-grant only |

`requires_approval: true` tools return a `bundle_id` that surfaces on the Relay; they never publish directly (LBI-04).

## Webhooks (outbound)

Signed (HMAC + timestamp + nonce). Events: `post.published`, `post.failed`, `bundle.generated`, `sub.expired`, `viral.labeled`, `incident.sev1`, `tos.blocked`. Consumers verify signature and dedupe on `event_id`.

## Rate limiting

Per-token buckets; `429` with `Retry-After`. Publishing to platforms is additionally governed by per-platform buckets in the worker (`L2.3`).

## Caption revision lifecycle

`POST /bundles/{bundleId}/revise` requires nonblank instructions (maximum 2000 characters). It atomically sets the bundle to `revising`, invalidates the prior ToS verdict, and enqueues the existing `content.generate` worker. The response describes queued work, not completed generation. The worker revises each existing platform caption using the operator instructions in S3, preserves the asset and hashtags, then returns the bundle to `generated` and enqueues a new `tos.scan`. This does not regenerate image/video assets.

Provider failure or unchanged output fails the job without changing captions or restoring approval. Failed generation is retried/replayed through the existing job/incident controls. Approval stays blocked while revision or its ToS scan is pending or failed.

The report carries a `revisionId` through scanning and into each Relay card. REST approve, revise, and reject actions on a revised bundle must echo this value; stale browser requests and stale Relay cards are rejected. These REST checks hold the bundle row lock through the mutation. Relay `revise`/`regenerate` use the same caption-generation path, accepting optional instructions or explicit default caption-revision instructions. Relay calls do not impersonate an AXIOM subscription user; they require an available provider that can operate without a user subscription identity.

Relay `edit_caption` follows the same approval invalidation rule without invoking generation: it stores the supplied text, assigns a fresh revision identifier, and enqueues a new ToS scan. Previously approved pending targets are canceled under their row locks, so even already-claimed jobs cannot publish the changed text using old approval. Any provider ID, published outcome, or unresolved dispatch blocks the edit until reconciliation. The operator must review and approve again, including selecting the new schedule.
